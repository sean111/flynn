# Flynn Desktop Companion

Flynn Desktop is a Tauri 2 + React/TypeScript companion for syncing the Flynn WoW addon's `Flynn.lua` SavedVariables file to the Flynn API. The native process owns filesystem access, API requests, PKCE exchange, and credentials; the webview never receives or persists the bearer token.

The shared [`docs/data-contract.md`](../docs/data-contract.md) is the source of truth for the export/import formats and data schema consumed by the desktop app and other Flynn components.

## Requirements and setup

- Rust stable and the platform prerequisites listed by [Tauri](https://v2.tauri.app/start/prerequisites/).
- Node.js 20+ and npm.
- Flynn API with desktop PKCE enabled. Configure `FLYNN_DESKTOP_REDIRECT_URI=http://127.0.0.1:51337/oauth/callback` on the API server. This is a fixed loopback callback; the desktop app verifies the OAuth state before exchanging the code.

```sh
cd desktop
npm ci
npm run tauri dev
```

From the repository root, `just desktop-test` runs the Rust workspace tests and build plus the frontend tests and TypeScript/Vite build. To run these directly from `desktop/`, use `cargo test --workspace`, `cargo build --workspace`, `npm test`, and `npm run build`. Release bundle: `npm run tauri build`. Rust lint checks: `cargo fmt --all -- --check` and `cargo clippy --workspace --all-targets --all-features -- -D warnings`.

## Usage

1. Choose or verify the detected World of Warcraft installation directory. The directory must contain `_retail_`, `_classic_era_`, `_classic_`, or `_forever_` flavor folders.
2. Select **Connect to Flynn**. The app creates a PKCE verifier/challenge and random state, opens the system browser to the configured Flynn API's desktop authorization flow, receives the one-time callback on `127.0.0.1:51337`, and exchanges the code in the native process. The bearer token is stored only in the OS credential store (macOS Keychain, Windows Credential Manager, or Linux Secret Service); no plaintext fallback is used.
3. Use **Upload Now** to sync discovered files, or enable Automatic Sync to watch them. The app waits for filesystem writes to settle, enforces the 10 MiB limit, hashes SHA-256 contents, and suppresses unchanged successful uploads. Successful hashes are namespaced by canonical API origin, authenticated Flynn user, and canonical source path. Before each POST, the app durably records an attempt keyed by source, content hash, and session fingerprint. HTTP 429 responses are retried at most three times using `Retry-After` when supplied; retries are cancelled if the active session changes during backoff. Other uncertain transport/server outcomes remain ambiguous to avoid duplicate ingestion. A `202 Accepted` response is saved with its dump ID and polled with bounded retries/backoff; if polling is interrupted or remains pending after five minutes, the app resumes status checks from the persisted API, user, and dump ID on the next launch/reconnect. The original source path is retained for display and bookkeeping only; a deleted or renamed file does not prevent checking an already accepted dump. Pre-POST file/stability errors, definitive rejection, and terminal failed/partial ingestion outcomes are remembered per content hash, so automatic reconciliation does not repeatedly send the same invalid dump; Upload Now can deliberately retry a definitive failure, and changed content can sync automatically. Persisted ambiguous and failed attempts appear in **Needs your decision** only when their exact content hash is still present in an enabled discovered file. A changed file therefore does not show a stale retry action; the old attempt is retained as duplicate-risk history and becomes actionable only if those exact bytes are current again. If a POST may have reached Flynn but its response is unknown, the app blocks automatic reposts, including after restart or reconnect. Use **Retry anyway (may duplicate)** only after reviewing the warning; the action explicitly confirms that Flynn may already have accepted the previous request. This is duplicate-risk mitigation, not exactly-once delivery. Per-character ingestion results and partial errors are shown in the activity list.

The API base URL is configurable in Settings. It must be an HTTP(S) origin/base URL; do not include `/api/v1` (plain HTTP is permitted only for local development). The native credential-store key is scoped to the API base, so changing servers attempts to remove the old local credential and requires a new sign-in; if old-key deletion fails, the new credential is rolled back and the old session remains bound. Persisted state is serialized by taking each config snapshot only after the save lock is acquired, preventing a queued older write from replacing a newer submission or pending-dump record. Successful hashes are cleared on logout and fenced/reset when the API server or Flynn user changes. Pending dump IDs remain tagged to their exact API base and user so they can be resumed only in the matching session. The WoW root, auto-sync setting, sync exclusions, launch-at-login setting, minimize-to-tray preference, successful content hashes, pending dump IDs, submission attempts, and activity history are stored in the user's app config directory. **No access token is written to app settings, logs, or frontend state.**

Logout first commits a signed-out config before deleting the OS credential. If config persistence fails, the keyring credential is retained and the previous persisted session binding remains intact. If OS credential deletion fails after the signed-out config commits, Flynn stays signed out and persists a cleanup warning; the unbound credential is not used for API requests. The current API does not expose a desktop-client token revocation endpoint, so server-side revocation must be done in browser-managed Flynn account settings. The app explains this limitation at logout.

Settings are written through a temporary file that is flushed before atomic rename. On Unix Flynn then attempts to sync the containing directory. If that sync fails, the rename is already committed: Flynn keeps the new settings, shows a durability warning, and makes a best-effort second atomic write to include that warning. The second write does not retry the directory sync, so neither the latest rename nor the warning is guaranteed to survive sudden power loss. On non-Unix platforms (including Windows), parent-directory sync is currently a no-op; the temporary file is flushed before rename, but Flynn does not claim the rename itself is durable across sudden power loss. A failure to persist the warning may leave it visible only until the app exits.

## Sync behavior and safety

- Discovery is scoped to `<WoW root>/{_retail_,_classic_era_,_classic_,_forever_}/WTF/Account/*/SavedVariables/Flynn.lua`; WoW Forever is shown as a distinct flavor and never aliases another install. On macOS and Linux, upload reads anchor an opened handle at the selected WoW root and walk each path component with descriptor-relative no-follow opens. On Windows, the reader anchors at the volume root and opens each component relative to the already-open parent handle with `NtCreateFile(FILE_OPEN_REPARSE_POINT)`, inspecting every opened handle and rejecting reparse points. Neither path follows a swapped symlink/junction out of the selected root. Windows runtime tests still need to be executed on Windows before treating that platform as release-verified. Account/flavor toggles can exclude a source.
- Filesystem events are debounced and reconciled with a startup/rescan pass so missed OS notifications do not permanently miss a dump.
- Files over 10 MiB are not read or uploaded. Uploads send the original file as multipart `file`; they do not parse or execute Lua.
- Successful hashes are recorded only after a terminal successful ingestion and are scoped by API origin, Flynn user, and canonical file path. Known rejected/failed or partial ingestion remains visible and can be retried with Upload Now. Unknown POST outcomes are persisted as ambiguous and cannot be automatically retried; an explicit user confirmation is required, and retrying may create a duplicate.
- Session generations and the captured API/user/token identity fence stale `/me` retries, upload/status responses, activity updates, pending-dump changes, and successful hashes when logging out, changing API server, or switching authenticated account. Signed-out status reads revalidate their captured generation and unbound local credential binding before returning; a leftover OS credential after a failed cleanup does not reactivate that binding. A same-identity relogin is still a new generation, so a stale completion cannot write state for it. Requests already handed to the HTTP stack may still have reached the server; session fencing cannot undo server-side processing.
- Pending asynchronous dump IDs are persisted and account/server fenced. Status polling uses bounded HTTP timeouts, retries transient status-check errors with exponential backoff and `Retry-After`, and never re-uploads a dump merely to check its pending status. Polling resumes by persisted dump ID even if the source file has been deleted or renamed.
- An API 401 commits the signed-out config before removing the unusable local credential. If config persistence fails, the credential and previous persisted binding are retained together. If keyring deletion fails after config commit, the app immediately returns signed-out status with a persisted cleanup warning and does not use the unbound credential; deletion diagnostics use stable sanitized error codes rather than raw keyring errors. Other network/API diagnostics are surfaced without response dumps, payload contents, or credentials.
- Closing the window hides it when minimize-to-tray is enabled. Use the tray menu to reopen or quit.

## Tests and limitations

`just desktop-test` runs `cargo test --workspace`, `cargo build --workspace`, `npm test`, and `npm run build`. Rust tests cover WoW discovery and safe reads (including file/parent swaps and platform-specific link handling), flavor/account extraction, scope toggles, installation-root detection, bounded file reads and hashing, injected credential-store sharing/isolation, cross-server rollback, immediate signed-out status after an expired-token 401 even when keyring cleanup fails, sanitized keyring diagnostics, warning cleanup on same-API relogin, stale signed-out status and `/me`/response/new-login races, session cancellation, crash-window attempt visibility/actionability after restart without auto-POST, confirmed retry through the command against a mock HTTP server, source-deleted pending-ID polling, current-hash-only ambiguous/failed presentation, deterministic concurrent settings/scope/launch mutations, serialized concurrent saves, persisted pre-POST/ingestion failures, rejection/ambiguous/changed-content retry behavior, 429 retry success and cancellation during backoff, atomic settings failure handling, session-scoped hash keys, retry delay selection, PKCE primitives, safe API error parsing, queued-vs-terminal receipt handling, partial results, and stable-file sampling. Frontend tests include mocked-Tauri App.tsx integration coverage for login/logout response races, persisted crash-window attempts surfaced outside activity history, refreshes requested during settings mutations, and out-of-order command responses, as well as status-guard unit coverage for command-vs-refresh and command-vs-login races. Windows tests assert that symlink/junction fixtures are actual reparse points before checking rejection at path components and during swaps; **Windows acceptance remains unverified until these tests have been run successfully on Windows**. Some Windows fixture creation requires Developer Mode or elevation, and setup failure intentionally fails the tests rather than silently passing. Browser-based auth, live Keychain/Credential Manager/Secret Service access, tray behavior, and live filesystem notifications should also be smoke-tested on each supported OS. The native build explicitly selects the platform keyring backend; OS credential-store absence or lock errors fail closed, with no plaintext token fallback.
